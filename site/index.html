    A software factory on Azure

    Executive · About 10 minutes to read, excluding the FAQ

    Technical · About 20 minutes to read, excluding the FAQ

    What triggers the factory? In Phase 1, a team member opens a GitHub issue to request a change. Later, a signed-in form or an internal service could submit the same request. The Build Orchestrator starts coding once the sponsor approves the scope or a standing repair policy covers it.

    Phase 1 delivers the factory to one operations team. It builds and maintains Screening Desk, the replacement for the team’s legacy shift tracker. Phase 2 adds connectors or serves another team.

    Assumptions

    The organization ruled out AI app builders for this project. Its engineers need to adapt connectors and permissions as legacy systems, databases, the ERP and external services change. They review code in GitHub and release to Azure. The team knows the factory model and can reuse earlier templates and runbooks.

    We chose an Azure-hosted Claude Code worker over Claude Code’s GitHub integration for the flexibility to adapt intake, connectors and approvals to each project.

    The pilot assumes the team can get a sample export from the legacy tracker and observe a shift handoff. Engineers use both to check that the next shift can find each open issue, its owner and its follow-up time in the new app.

    Inside the Azure factory

    The factory takes a team’s request from an approved change to a tested app running in Azure.

    Azure deployment map

    The Build Orchestrator starts Claude Code in an Azure Container Apps sandbox. Independent CI tests its patch in a fresh sandbox before an engineer reviews it in GitHub.

    What does the Build Orchestrator decide?

    The orchestrator is a TypeScript service on Azure Container Apps. It takes approved work from one queue, whichever channel submitted it. Its workflow rules run without an LLM. A coding attempt may last minutes while an access decision takes a day. The orchestrator keeps the task and approval history in PostgreSQL so it can release the sandbox, then resume with the owner’s current grant. GitHub keeps the pull request and its review.

    1. Claim and authorize

      Claim the current attempt in PostgreSQL. Confirm dependencies, current sponsor access and remaining budget. For a changed permission scope, hold dispatch for a new owner decision.

    2. Dispatch and checkpoint

      The orchestrator uses its managed identity to create a sandbox. Give Claude Code the pinned source, approved tools and expiry. Record the candidate revision before queuing verification. GitHub writes go through the broker.

    3. Reconcile a retry

      If the orchestrator loses the reply after the broker opens a PR, the next attempt checks GitHub using the original operation ID. It records the existing PR before continuing. Late results from the old attempt are rejected.

    The recorded states for this path are queued → running → verifying → awaiting_review. A run waiting for review releases its sandbox. Proposed beta limits are one writable run per project, two concurrent generation runs across the workspace and 20 minutes per generation attempt.

    When does a beta change need an engineer?

    How does MCP connect the agent to business systems?

    Model Context Protocol (MCP) lets Claude discover and call named tools with typed arguments. The orchestrator grants tools per run. The MCP server authorizes each call before an adapter queries a database, legacy app, knowledge base, ERP or external API. Beta grants read access. Write tools would need separate approval and retry rules.

    What can move the dates?

    Access to information is the biggest schedule risk. The team needs source contracts, representative records and business owners who can explain rules and exceptions. A two-week access delay moves beta from Week 10 to Week 12.

    The six-week build assumes a full-time technical lead, half-time platform engineer and existing Azure landing zone. Reforecast at Week 3 if the starter, network access or sample records are missing.

    Frequently asked questions

    Deployment troubleshooting
    What does the factory add to GitHub and Azure?
    GitHub hosts the code and review. Azure runs the workloads. The factory connects the approved brief, the agent’s permissions, the independent test results and the exact release so a team can trace what it authorized all the way to production.
    Where does the Claude Code worker run?

    In the proposed factory, the worker runs in a temporary Azure Container Apps sandbox in the company’s subscription. It has its own copy of the approved repository revision. When it returns a patch, the factory can discard the sandbox. The next attempt gets a fresh one.

    The worker uses the Claude Agent SDK. Its file edits and shell commands run inside the sandbox. Model requests go through the gateway to the configured Claude deployment in Microsoft Foundry. The GitHub broker opens the PR and a separate verifier runs protected checks. Azure sandbox lifecycle · Claude on Microsoft Foundry

    Does the Build Orchestrator use an LLM?

    No. It is a shared TypeScript service. It checks the approved scope, starts the coding job, sends the patch for testing and counts attempts. When a check fails, a recorded rule allows one repair within budget. If the repair fails, an engineer receives the patch and failure. The shift coordinator in Screening Desk is a person using the finished app.

    The orchestrator records each decision in PostgreSQL. When several reviewers find problems, it can collect their findings into one work item. Claude interprets those findings. The sponsor or data owner decides any change in scope or access.

    Who runs the subagents, and which specialists does a change need?

    In Phase 1, only the Claude Code builder edits the source. It calls read-only specialists through the Claude Agent SDK, so reviewers can inspect the same patch without changing it. For the legacy replacement, discovery maps booking IDs before coding. After the patch, the code reviewer looks for duplicate imports, the security reviewer checks viewer permissions, and the UX reviewer tries the handoff with a keyboard. These three reviews can run in parallel.

    A small query fix can use the builder and the protected regression test alone. The factory defines available roles, required reviews and tool permissions. Specialists report findings to the builder. The engineer reviews the verified patch.

    Each specialist gets a separate conversation in the same coding sandbox. All model calls count against the same run budget. If a required review is missing, the orchestrator holds the change for review. See the subagents in the architecture diagram. Claude Agent SDK subagents

    How many containers or sandboxes does one change use?

    A first-pass change uses two temporary sandboxes. The builder and up to four specialists share one coding sandbox. A fresh verification sandbox then runs the tests.

    One repair and retest bring the total to four. The repair gets a new coding sandbox and a new verification sandbox. This counts allocations over the life of one change. The shared orchestrator, gateway and deployed app have their own lifetimes.

    The proposed pilot allows two coding attempts at the same time across projects and one writable attempt per project. A specialist requiring a different security boundary would run as a separate isolated job and add to the count.

    Is the independent test runner another Claude Code agent?

    No. It is a separate continuous integration (CI) job running without Claude. The builder can run local tests while editing. The independent runner executes protected checks in a clean sandbox and records which revision produced each result.

    Assign an owner to Hall B while its delivery is overdue. The original code hides the booking. The patched code keeps it visible until the delivery arrives. The engineer sees both results from the same test before reviewing the PR.

    A future test-design subagent could suggest another case, such as assigning the booking twice. That suggestion can become a test. Only an executed protected check supplies independent pass or fail evidence.

    How does the factory prevent an infinite loop?

    The pilot gives Claude 20 minutes per generation attempt and one chance to repair a failed check. If Hall B still disappears after that repair, the orchestrator stops and sends the failing check and patch to an engineer. The run also stops when it reaches its token or spending limit.

    A transient infrastructure error can trigger up to two retries. The orchestrator records attempts, failures and budget usage under the run ID, so a restart preserves the limits. A repeated verification failure ends automatic repair. If a GitHub write timed out, the orchestrator checks whether it succeeded before retrying.

    When does the factory need human intervention?

    A low-risk repair covered by an existing policy can start automatically. A sponsor decides if the requested behavior is unclear or the scope grows. The owner of a connected system approves new access, such as reading two fields from the booking feed.

    When a repair still fails or a run hits its budget, an engineer reviews the patch and the reason it stopped. They can close the request or revise the task for another authorized attempt. During beta, an engineer reviews verified code before merge. After staging passes, the release owner approves the production deployment.

    A corrected patch goes through verification again. A schema change also needs the database owner’s approval for the migration and recovery plan. See where each person records the decision.

    Can a team request a build outside GitHub?

    Yes. The pilot uses the team’s GitHub intake repository. Later, a shift lead could sign in to an internal form to report a missing Hall B booking, or an approved incident service could send that report through an API. Either could create a factory request directly. Engineers would still review the resulting patch on a GitHub pull request.

    Each channel must identify the caller and check their right to submit for the team. The intake API records the channel, source ID, requester, team and expected result. A retry with the same caller, channel and source ID in that team returns the original request ID. The Build Orchestrator can dispatch work only after scope approval or a matching repair policy.

    Where do people approve a change?

    The sponsor approves its scope on a pull request or follows an email invitation, signs in and confirms. If the app needs new access, the owner of that system approves the specific operations through either channel.

    The engineer reviews the code and test results on the change’s pull request. After staging passes, the release owner approves the production job in GitHub Actions for the tested image and its Azure destination.

    The factory records who decided, when, and which scope, commit or image they reviewed. Forwarding an email gives the recipient no approval rights. A changed scope, commit or image needs a new decision. If the private repo’s GitHub plan lacks deployment reviewers, the release owner approves a protected release PR naming the same image and target. Actions deploys the approved release. Jira is optional status reporting after handover.

    What does a second team have to bring?

    The festival team uses the factory to build Screening Desk. The portfolio team comes next with a request for its own app, Project Library. Any portfolio user should be able to find “Depot retrofit.” Only editors should be able to add a review note. The team names who approves the work, who will maintain the code and who can authorize access to the catalog.

    The factory uses the same app template, testing tools and release process to set up Project Library in its own GitHub repository and Azure environment. It runs the portfolio team’s example in a private preview so the team can check the result.

    Project Library uses two database accounts. One can read approved entries in the existing catalog. The other can save notes in the app’s own database. The app checks whether the signed-in user is an editor before saving. Tests check that an editor can save and reopen a note, a viewer’s save is denied, and the catalog account cannot change the original project record.

    What can an app do with an ERP connector?

    A released app can read or write ERP records when the system owner grants that operation. Screening Desk reads a maintenance ticket and saves the handoff note in its own database. Another app could have permission to update a work order in the ERP.

    Staff can start a handoff themselves. If the team also subscribes to ticket changes, an ERP event can open a handoff inside Screening Desk. That event goes only to the running app. To change the software itself, the team submits a separate factory request.

    The app uses its own runtime identity. Ticket reads, work-order updates and event subscriptions require separate grants. The receiver checks the sender and hall and records the event ID to avoid duplicate handoffs. The coding agent uses synthetic tickets.

    When would the factory refuse to ship?
    Suppose the overdue-list fix passes on revision A and someone pushes revision B. The factory holds the merge, shows the engineer which checks need repeating and requires fresh evidence for B.

    After merge, the release controller checks the image built and tested in staging. It can promote only the digest the release owner approved for that environment.

    What does Week 10 cover?
    The beta opens once the team can use the generated replacement and get a verified fix through the same factory. The old tracker stays in use during feedback and monitoring. After sign-off, allow 2–4 weeks for the final import, production switch and operator handover to complete Phase 1.

    Sign-off at the end of Week 12 puts handover in Weeks 14–16. If ERP access is ready then, a 3–5 week lookup could ship in Weeks 17–21.

    What comes after the first production release?

    Start with the question staff keep leaving the app to answer. A ticket might come from an ERP, an asset record from a database view, or a delivery update from a partner API. The factory can also build the next team’s app using the same starter and release process.

    For the ERP example, accept the lookup when a coordinator can read the assigned hall’s ticket, another hall’s ticket is denied, and an ERP outage still allows a plain note. Add event delivery when staff need automatic handoffs. Trial indexed search, extra agents or automatic merging when reviews show where the existing process costs time. Jira can mirror status.

    Why did the organization choose a software factory?

    Consider one shift handoff. The legacy booking system owns the screening time, the ERP owns the maintenance ticket, and Screening Desk owns the coordinator’s note. Each owner decides what staff can read or change. The organization chose the factory so its engineers can adapt each integration as those rules evolve.

    If the ERP changes a ticket field, an engineer can update its adapter in GitHub. The verifier checks that the coordinator can read Hall B’s ticket, that another hall’s ticket is denied, and that staff can still save a plain note during an ERP outage. The release owner approves the tested image for the app’s Azure environment.

    How will we know which parts to reuse?
    Start with templates, tests and runbooks from prior factory work. Try them on a representative request under this organization’s permissions. During beta, compare time to a verified preview, engineer review time and escaped defects with similar manual changes.
    What happens to open issues when staff switch apps?
    1. Map and rehearse

      Follow one open issue

      Map legacy issue 108 to booking F17-42, its owner, due time and latest note. Rehearse with an approved export in restricted staging. The agent develops against synthetic examples.

    2. Compare and decide

      Account for every open item

      Compare the source and target by issue ID and fields. Re-importing the same export must produce zero duplicates. An unknown owner, orphan booking or missing note holds the switch for the operations lead.

    3. Switch the team

      Use one writable register

      The operator freezes old edits, imports the final export and repeats the checks. The lead accepts the first shift in the new app. If checks fail, reopen the old tracker. After staff begin writing in the new app, preserve and reconcile those changes before any switch back.

    Why use PostgreSQL for orchestrator state and dispatch?

    The factory already needs to remember approved scope, revisions and checkpoints. With pg-boss it can save a checkpoint and queue the next job in one PostgreSQL transaction. If that transaction fails, neither write takes effect. That keeps a crash from leaving a task marked ready with no job to run.

    The beta team operates one shared store for state and dispatch. A database outage therefore pauses both. GitHub writes happen outside this transaction, which is why the broker checks for an existing pull request before retrying. The generated app can use its own database. pg-boss transaction documentation

    Deployment troubleshooting

    The first build is queued. Why hasn’t a sandbox started?
    The platform engineer checks the dispatch lease. If the orchestrator claimed the run, inspect the sandbox creation error. For a quota error, check available cores in the region. For an access denial, check the orchestrator identity’s role on the sandbox group. After the fix, run one synthetic build and verify sandbox cleanup before releasing queued work. Sandbox quotas
    The sandbox starts. Why does the first model request time out?
    The platform engineer checks whether the request reached the model gateway. If it did, resolve the Foundry hostname from the gateway’s network and compare the result with the approved private endpoint IP. If it didn’t, check the sandbox route to the gateway. Resume generation after a synthetic prompt succeeds over the private path. Private endpoint diagnostics
    Why does the ERP lookup pass tests but return 403 in staging?
    The independent tests use a fixture. The app owner traces the staging request to see whether the connector or the ERP denied it. With the ERP owner, check the app’s runtime identity, the coordinator’s hall assignment and the approved ticket fields. Accept the integration when Hall B succeeds for its coordinator and another hall still denies access.
    The image was published. Why is the new revision still unready?
    The release owner checks the failing Container Apps revision’s system logs. For an image pull failure, verify the registry digest and pull identity. If the container started, check its console logs, listening port and readiness probe. Keep traffic on the healthy revision until the staged image passes readiness and the staff smoke test. Container Apps deployment diagnostics
    Is rollback safe if the canary fails after a database migration?
    The release owner stops promotion. The database owner checks whether the previous app revision can still read and write the migrated schema. If compatible, return traffic to that revision and verify a saved handoff note. Otherwise, pause affected writes and use the rehearsed repair or restore procedure, accounting for notes saved since the migration.
