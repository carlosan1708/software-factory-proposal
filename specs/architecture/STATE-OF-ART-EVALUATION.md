# Software Factory state-of-the-art evaluation

**Pilot decision** Use the Claude Agent SDK for coding, Azure Container Apps Sandboxes for direct execution, and PostgreSQL with pg-boss for factory checkpoints and dispatch. Each generated project selects its own source connectors and write store. We chose the Azure-hosted worker so teams can adapt intake channels, connector access and approval rules across projects. The Claude Code GitHub Action remains an optional benchmark for repository tasks.

**Evidence basis** Public product documentation and release notes as of November 18, 2026. Runtime behavior, cost, and organization-specific access are pending validation. The [factory architecture](SOFTWARE_FACTORY_ARCHITECTURE.md) describes the system and rollout. The [Screening Desk redesign](../presentation/PRESENTATION_REDESIGN_SPEC.md) defines the current walkthrough, and the [operations spec](../presentation/OBSERVABILITY_AND_OPERATIONS_SPEC.md) defines the Observability tab and production handover.

## 1. How the options were evaluated

Phase 1 covers one internal delivery team, one Next.js starter, and one active implementation task per project. A project can span weeks. It progresses through short runs and can wait for a human decision between them.

The evaluation applied the requirements below before comparing time to first PR, infrastructure to operate, and ongoing engineering effort. A documented feature counts as a capability. A feature that requires an adapter, administrative approval, or a runtime check is treated as conditional. The comparison uses qualitative judgments pending measurements from the beta build and participant use.

| Requirement | What would satisfy it |
| --- | --- |
| Actual Claude Code execution | The integration runs Claude Code's tools and agent loop. Confirm the approved authentication and Microsoft Foundry model route in the target environment. |
| Azure execution boundary | Run generated code on organization-controlled Azure compute. Prove that the generation environment reaches the scoped model gateway and only those trusted connector or retrieval broker routes approved for the task and that the verifier can run without outbound access or privileged credentials. |
| Durable project progress | Resume an approved plan after a restart. A pending scope or data-owner decision leaves independent work eligible and preserves finished milestones. |
| Authority and evidence | Recheck the sponsor's current access before a repository write. An independent verifier binds evidence to the exact candidate and base. Separate approval controls production release. |
| Sustainable operations | Support observable retries, cancellation, cleanup, and recovery. Count the ongoing effort of hosting, identity administration, and on-call response alongside initial setup. |

Compare full delivery approaches against these requirements. Compare SDKs, sandboxes, and queues within their own layers. For example, compare pg-boss with a workflow engine on dispatch and recovery, and evaluate the end-to-end stack on approvals and releases.

Public benchmarks provide context for the coding task. SWE-bench measures issue resolution, and ProgramBench tests whether agents can rebuild software from a binary and documentation. Use the factory's own scenarios to evaluate greenfield delivery, delegated permissions, review effort, and release evidence. [SWE-bench](https://www.swebench.com/) · [ProgramBench](https://programbench.com/)

## 2. State of the art and the strongest alternatives

- **Repository automation now comes with stronger controls.** GitHub Agentic Workflows reached general availability on October 28, 2026. It supports self-hosted Actions Runner Controller runners, separates agent work from permission-controlled writes, and offers staged previews of proposed writes. November releases added artifact-backed continuation. Test it as a serious reuse option for repository-level automation. [General availability](https://github.blog/changelog/2026-10-28-github-agentic-workflows-generally-available/) · [Staged mode](https://github.github.com/gh-aw/reference/staged-mode/) · [November release notes](https://github.github.com/gh-aw/blog/2026-11-09-weekly-update/)
- **Managed agent hosting has narrowed the gap.** Microsoft Foundry Hosted Agents supports custom harnesses including the Claude Agent SDK. Egress enforcement and opt-in resilient execution are generally available. Direct session-compute operations such as command execution and port management remain in preview. Recovered jobs can rerun the application handler, so checkpointing and reconciliation still matter. [Supported harnesses](https://devblogs.microsoft.com/foundry/introducing-the-new-hosted-agents-in-foundry-agent-service-secure-scalable-compute-built-for-agents/) · [Ignite updates](https://devblogs.microsoft.com/foundry/hosted-agents-foundry-agent-service-ignite-2026/) · [Session compute](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agents)
- **Disposable Azure worker isolation is generally available.** Azure Container Apps Sandboxes offers isolated microVMs and direct lifecycle controls. The factory can use separate short-lived environments for generation and verification while saving project progress outside both. Confirm quotas and the exact private network paths in the target subscription. [Azure Sandboxes general availability](https://techcommunity.microsoft.com/blog/appsonazureblog/azure-container-apps-sandboxes-now-generally-available/4559125) · [Sandbox architecture](https://learn.microsoft.com/en-us/azure/container-apps/sandboxes-overview)

## 3. Why this combination is the best pilot fit

### Claude Agent SDK gives the factory control over each coding run

The TypeScript SDK runs the Claude Code binary and exposes tools, permission controls, hooks, and session events. The controller can start a run from the approved task, pinned base commit, and repository conventions. It can stop the run, record usage and outcomes, and collect a candidate patch. Keep GitHub writes and deployment in trusted services. This preserves Claude Code while letting the factory enforce the same controls across initial scaffolding and subsequent changes. [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview) · [Secure deployment](https://code.claude.com/docs/en/agent-sdk/secure-deployment) · [Claude Code on Foundry](https://code.claude.com/docs/en/microsoft-foundry)

### Azure Sandboxes give generation and verification separate environments

Azure Container Apps Sandboxes provide disposable microVMs, image selection, lifecycle APIs, and per-sandbox network policy. Use one microVM for generation and a fresh one for verification. Set full traffic inspection and default-deny at creation. Permit the model gateway and, for tasks with named read grants, the corresponding broker endpoints. The broker holds upstream credentials and checks authority on each operation. Run verification with denied outbound traffic, synthetic fixtures, and trusted test instructions. Keep provider, GitHub, and production credentials outside both environments. The proof is the artifact and evidence the verifier produces for that commit. During implementation, establish the target subscription's quota, identity grants, routes, DNS, and real Foundry streaming behavior. [Azure Sandbox architecture](https://learn.microsoft.com/en-us/azure/container-apps/sandboxes-overview) · [Egress policies](https://learn.microsoft.com/en-us/azure/container-apps/sandboxes-egress-policies) · [Azure-hosted Foundry model options](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/claude-models-hosting-comparison)

### pg-boss keeps dispatch close to durable project state

The factory already needs PostgreSQL for milestone dependencies, sponsor approvals, audit events, and run status. pg-boss can insert a job in the same database transaction that makes a task eligible. A failed transaction leaves both unchanged. pg-boss supplies retries and job expiry, and delivery is at least once. The worker records stable operation IDs and reconciles ambiguous GitHub writes before retrying. A project awaiting a decision parks its state in PostgreSQL and schedules another short job when it can proceed. [pg-boss delivery semantics](https://pgboss.io/introduction) · [Transactional scheduling](https://pgboss.io/api/adapters)

The trade-off is a shared failure and capacity boundary for state and dispatch. Monitor queue age, retry patterns, database load, and connection usage. Revisit Service Bus when dispatch needs a separate failure boundary or cross-service consumers. Evaluate Azure Durable Functions with Durable Task Scheduler when parallel milestones, durable timers, or complex approval dependencies materially increase the recovery logic the team owns. Temporal is credible when the organization already operates it. LangGraph is a candidate for complex branching inside an agent task. [Service Bus reliability](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-message-loss-and-duplicates) · [Azure Durable Functions TypeScript example](https://learn.microsoft.com/en-us/samples/azure-samples/durable-functions-quickstart-typescript-azd/starter-durable-fan-out-fan-in-typescript/) · [Temporal self-hosting](https://docs.temporal.io/self-hosted-guide) · [LangGraph interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts)

**Cost of the choice.** A packaged tool can produce a first PR sooner. The proposed stack adds a controller, a model gateway, a sponsor-aware GitHub broker, durable approval records, and infrastructure operations. Those components are justified when the organization needs to enforce its own authority and release rules. If the pilot scope becomes recurring changes to a single repo with standard human review, reevaluate the simpler GitHub Action setup.

**Release evidence.** Use SLSA provenance as the reference for tying an image digest to its source commit and trusted builder. Bind the independent test record and release approval to that same image digest. Build provenance establishes the artifact's origin. The verifier establishes whether behavior passed the required tests. GitHub attestations for private repos require Enterprise Cloud. For an Azure-native path, assess Notation with Azure Container Registry and have the release controller verify the signature and evidence before promotion. [SLSA provenance](https://slsa.dev/spec/v1.2/provenance) · [GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations) · [Azure OCI signing and verification](https://learn.microsoft.com/en-us/azure/container-registry/overview-sign-verify-artifacts)

## 4. Acceptance checks for the app-producing beta

Build and test the supported SDK path in the approved development repository. If comparing a repository automation alternative, reuse these two tasks: the Screening Desk starter and an assigned-booking regression against a pinned revision. Supply the same synthetic schedule, approved guidance, and note-store contract to both paths. Exercise live broker controls separately on each path that claims them. Use the same model deployment where supported, equivalent time and token budgets, and the same independently maintained acceptance checks. Record differences in runner, credentials, approval wait, and model where they affect comparability. Repeat each coding scenario and report attempts, acceptance rate, and cost per accepted change, counting failed attempts in the cost. Treat this small sample as preliminary engineering evidence.

Exercise the factory-specific scenarios below on the proposed stack. Add GitHub Agentic Workflows to the comparison if the team can validate its approved runner and Foundry path. If Foundry Hosted Agents is available under the target policy, compare its generation path against the same network, identity, and evidence checks while keeping verification independent.

| Scenario | Required result |
| --- | --- |
| Greenfield starter | A project generated from the brief runs from a clean checkout, builds successfully, and passes independent browser checks for the overdue master for the 18:30 Hall B booking, a received master, and a booking whose deadline is still ahead. An authorized lead can assign follow-up and a viewer is denied. |
| Legacy app replacement | Rehearse the same export twice and confirm one target record per open legacy issue ID, with the expected owner, due time and note. Exercise a missing owner and a failed import. Hold cutover, keep the old tracker usable, then repeat the final reconciliation before staff switch. |
| Scoped regression fix | A trusted test fails for the expected reason on the base and passes on the candidate. Assign an owner to the overdue booking. The base hides it, the candidate keeps it visible, and confirmed receipt clears it. Record both revisions, the test run and resulting artifact digest. |
| Stale review and revoked sponsor | Change the PR head after approval and revoke sponsor access before a write. The current check and broker block the corresponding operations. |
| Isolation and cleanup | Confirm the approved model request works from the generation VM. Exercise each granted broker read, deny an ungranted operation, and check that unapproved public, private, and non-HTTP traffic is blocked. Confirm the verifier has no outbound route and that cancelled or expired sandboxes are reclaimed. |
| Worker restart and duplicate delivery | Interrupt the worker after a successful sandbox or integration call and before local completion. On retry, reconcile the prior effect and end with one intended PR. |
| Production authorization | An approved PR and green build can reach staging. Hold production until the release owner approves the protected Actions job for its staged digest and target. Exercise a rejection, a replaced digest and a rerun. Each must hold production pending a current decision. For repositories configured with the release-manifest PR gate, verify that changing the digest dismisses review and that deployment reads the approved, merged manifest. |
| Multi-week project behavior | Park schedule export for a named data owner while the schedule view proceeds. Restart the worker. A ticket transition, expired invitation or sign-in by another user must leave export blocked. An authorized owner confirms the current fields and recipients on a scope PR or through a signed-in email invitation. A duplicate confirmation must leave one decision, and dispatch still requires current sponsor authority. |

Capture setup effort, time to a verified app preview, reviewer minutes, inference and compute usage, blocked writes and retry outcomes. Record access wait separately. Open beta when participants can generate real apps from authorized briefs and review independently verified previews. Monitor beta runs and check participant feedback against the resulting revisions. Test digest mismatch and rehearse rollback before the release owner promotes the approved artifact. Release timing follows the [beta and production release spec](BETA_TO_PRODUCTION_SPEC.md).

## 5. Review of the expanded Screening Desk proposal

The Phase 1 acceptance checks cover one approved programming API, versioned starter guidance, one app-owned store and recovery after an interrupted run. Use the expanded examples below to evaluate individual Phase 2 extensions after production handover. The factory can support more combinations as their owners supply contracts, identities, representative fixtures, and recovery procedures. The earlier Project Library example illustrates a relational deployment. Screening Desk exercises a different combination.

| Decision | Recommendation and evidence to collect |
| --- | --- |
| Database selection | Use the programming API as the authority for screening times and Azure SQL as the reference write store for coordinator notes. Existing SQL Server, MySQL, PostgreSQL, or document stores are candidates per project. Select by ownership, transactions, query patterns, and recovery needs. For Screening Desk, run tests against a compatible SQL engine with separate staff and migration permissions. Exercise a note write, denial of a source write, and restoration of saved notes. Qualify a document adapter with its own partition, concurrency, and access tests when a project needs one. [Azure data models](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/data-store-overview) |
| Internal systems | Evaluate the [factory MCP endpoint](SOFTWARE_FACTORY_ARCHITECTURE.md#agent-access-through-mcp) with the same typed legacy schedule operation under a task-scoped grant. Measure authorized results, added latency and integration effort. Test a different festival, revocation and upstream timeout. The released app uses its own runtime identity. For the handoff-note feature, exercise its hall-scoped ERP lookup and the separate app database write against representative fixtures. An existing approved Azure API Management gateway is a hosting option for the endpoint. [Azure API Management MCP support](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview) |
| Retrieval | Use versioned exact lookup for Phase 1. In Phase 2, compare it with Azure AI Search hybrid retrieval on the same runbooks and API contracts. A Foundry IQ knowledge base is a managed alternative when the team needs retrieval across multiple approved sources. Score whether the cited passage supports the answer and whether it is current. Revoke one reader’s access after a successful query, repeat it, and check excerpts, citations, and cached results. A schedule change must come from the schedule API. [Azure retrieval choices](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview) · [Document permissions](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview) |
| Subagents and sessions | Compare the builder alone on the bounded bug with risk-routed discovery, code, security and UX reviews on representative changes. Measure missed dependencies or permission errors found, reviewer minutes, accepted fixes, elapsed time and combined token use. Replay the same change with and without the relevant specialist to isolate its contribution. The independent CI runner supplies merge evidence. Interrupt after PR creation and before checkpoint completion. A fresh attempt must recover the approved plan, preserve the deferred export, and reconcile the existing PR under current grants. [Claude SDK subagents](https://code.claude.com/docs/en/agent-sdk/subagents) |
| Cost and observability | OpenTelemetry and Application Insights should distinguish a late factory preview from a released app waiting on the programming API. Trace a retry back to its originating attempt and include all specialist calls, reconcile spend across **all** attempts, then divide by accepted changes. Report fixed database, search, and telemetry costs separately. Keep approval and release records unsampled. Trial Langfuse or an already approved LangSmith instance only if it improves the time to diagnose or grade the same synthetic case. [Observability tooling decision](OBSERVABILITY_TOOLING_DECISION.md) · [Azure Monitor sampling](https://learn.microsoft.com/en-us/azure/azure-monitor/app/opentelemetry-sampling) |

**Presentation and delivery.** The [presentation](../presentation/PRESENTATION_SITE_SPEC.md) illustrates three Screening Desk cases and a second team launching Project Library in one selectable animation. The ERP feature includes a live ticket lookup and an optional inbound change event that starts a pending handoff. During beta validation, trace a permitted project read to its source, confirm revocation takes effect on the next retrieval, recover a work item after a worker restart and reload a confirmed note after an app restart. Measure connector isolation, retrieval permissions, SQL restore and costs on the actual backend. The Week 10 beta opening estimate assumes one connector and one write adapter. Validate the first legacy MCP adapter within Phase 1. After handover, sequence the next integration or team in Phase 2 and estimate the time it adds. Production timing depends on feedback intake, monitored outcomes and release readiness.
