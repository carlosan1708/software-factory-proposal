# Two-phase factory delivery

The first usable delivery is an internal beta of the factory. Phase 1 invitees open a GitHub issue in their team’s intake repository to request a new app or change. A signed-in form or an internal service API could be added after the pilot if another team needs it. Approved work generates a working app or verified update. The team keeps that service available while it collects feedback and monitors actual use. The production release concludes delivery after feedback has been reviewed, required fixes have been verified, and the released service is healthy.

## Phase 1 · Replace one legacy app for one team

Use the factory to generate a web replacement for the release operations team’s legacy desktop shift tracker. Limit the first delivery to open issues, owners, due times and notes. Import those records from an approved export. Keep closed history available in the read-only old tracker. The separate booking feed is the only ongoing business integration. Runbooks and schema come from the starter, and the new register has its own database.

For example, at 16:15 the film master for an 18:30 screening in Hall B is still missing. The source deadline was 16:00. The shift lead uses Screening Desk to assign a coordinator to contact the distributor and check back at 16:30. Assignment leaves the booking on the escalation list until the source confirms receipt. During beta, compare elapsed time from the missed deadline to a named owner against the previous shift log.

Deliver one private app from one starter, one read-only MCP adapter for bookings, master delivery deadlines and receipt status, and one app-owned Azure SQL store for follow-up assignments and notes. The Claude Code builder uses a pinned runbook and schema from the starter. The legacy replacement demonstrates discovery and applicable code, security and UX reviews in the coding sandbox. The isolated CI test runner executes protected checks without a model call. The Hall B query repair illustrates the shorter route. Demonstrate a follow-up fix that keeps an assigned overdue booking visible, independent verification and human approval on the same path. Keep project isolation, revocation, durable checkpoints, monitoring, rollback and restore in the first delivery. These make the first team’s service supportable.

To open the beta around Week 10, demonstrate two outcomes with one operations team. First, the factory generates a usable Screening Desk preview. Reimporting 24 sample issues preserves every owner and note, creates zero duplicates, and the incoming coordinator can update an imported issue. Second, the same factory receives a follow-up GitHub issue for the Hall B defect. The independent check fails on the original revision and passes on the fix, and the coordinator confirms the assigned overdue booking stays visible in the updated preview.

Before switching staff, rehearse an idempotent import keyed by legacy issue ID, and compare each open item’s booking, owner, deadline and note against the export. During beta the old tracker remains authoritative. At cutover freeze old writes, migrate the final snapshot and obtain the operations lead’s acceptance of the first shift. If reconciliation fails, resume in the old tracker. After the switch, preserve new writes and reconcile them before any return. Reforecast if replacing the legacy app requires more feeds, historical backfill or two-way synchronization.

Use a versioned scope PR or an authenticated email invitation for sponsor and data-owner decisions. Engineers approve verified code in a GitHub PR. The release owner reviews the tested image digest and Azure target before approving the protected GitHub Actions production job. The factory retains the decision evidence. Optional Jira status reporting belongs after handover.

### Feedback intake and monitoring

Collect feedback from the generated app preview or the factory request page. Link the report to the app, factory run and revision. Ask what the participant expected, what happened and whether it blocks use. The lead assigns an owner and records whether the team will fix the issue before release, defer it with sponsor agreement, or close it with a rationale. Return a corrected preview to the reporter for confirmation when appropriate.

Start observation with the first beta user. Monitor successful app generation, verification failures, time to a usable preview, and errors on a representative journey in the generated app. Compare outcomes with participant reports. The reviewing engineer verifies release-blocking fixes and the operator reviews alert delivery, rollback and restore evidence. Keep beta open if feedback is absent, evidence is incomplete or a serious issue remains. New feedback can reopen a previously reviewed candidate.

### Timing and assumptions

Access to reliable information is the biggest schedule risk. During the first week, secure time with the business expert and system owner to review real workflow exceptions, current contracts and approved representative records. A working Azure account or GitHub repository alone cannot resolve what a connector should return or what a passing acceptance test means. Scope the estimate to one internal team, one starter and one approved read connector. Estimate additional integrations, ERP event delivery and another team's onboarding separately.

Assume an existing Azure landing zone, working organizational GitHub access, one hands-on lead and a half-time platform engineer, with reviewers and data owners available when needed. The six-week build allows about nine engineer-weeks. At the end of Week 3, confirm that the team has a usable starter, an approved model and network path, and representative source records with timezone-aware deadlines and delivery status. If the booking feed lacks these fields, review the scope with its owner before committing to the estimate. Reforecast the beta if those dependencies remain open. The security and integration work is part of the deliverable beta build. Budget a further **2–4 weeks after feedback and monitoring sign-off** for final release preparation, promotion, observation and handover, assuming the agreed scope and staffing. Separate active engineering effort from elapsed time awaiting feedback.

Show an open-ended beta bar from around Week 10. Anchor the production bar to feedback and monitoring sign-off, with a duration of 2–4 weeks. Access two weeks late moves the estimated beta opening to Week 12. Sign-off at the end of Week 12 implies completion in Weeks 14–16. Sign-off at the end of Week 15 implies Weeks 17–19. These examples support internal planning. Keep beta infrastructure and support in the operating budget while feedback is open.

## Phase 2 · Extend the running factory

After handover the same team uses feedback to choose the next improvement. Name the user problem, the person who can confirm it is solved and the access needed to test it. Deliver one extension at a time while the first team continues using the factory. Choose a database view for asset details, an existing legacy API for scheduling, a partner service for delivery updates or an ERP tool for maintenance tickets. The worked example lets a coordinator open Hall B’s ticket while writing a note. Choose by user need and source ownership.

For that read-only ERP lookup, allow **3–5 additional weeks once the ERP owner, contract and test access are ready**. This is an illustrative planning range for the existing delivery team. Allow one week to confirm ticket fields, hall mapping and sample cases, one to two weeks to implement the adapter and app change, and one to two weeks to verify permissions, handle outages and release. Close when an authorized coordinator can retrieve the current ticket, another hall’s ticket is denied, and an ERP outage still permits saving a plain handoff note. Re-estimate if representative records, test credentials or the ERP owner are unavailable.

A second team launching Project Library is an alternative first extension with its own estimate. ERP-triggered handoffs need a separate event contract and duplicate-delivery tests. Additional database or partner adapters, indexed retrieval, specialist agents, live auto-merge and one-way Jira reporting can follow as usage identifies a need. Estimate each when its scope is known.
